## VEREDITO

**RECOMENDO A OPÇÃO B. O atual artifact `air-java` deve manter suas coordenadas
no módulo físico `air-model`.** O root passa a `air-java-parent`, com packaging
`pom`, exercendo agregação e herança. `validation` permanece junto do modelo.
Nenhum package Java público deve ser renomeado.

```text
air-java/                         repositório, não coordenada do parent
├── pom.xml                       io.github.gustavo2358:air-java-parent (pom)
├── air-model/
│   ├── pom.xml                   io.github.gustavo2358:air-java (jar)
│   └── src/{main,test}/java/     model + validation + suíte existente
├── air-json/
│   └── pom.xml                   io.github.gustavo2358:air-json (jar; vazio em 0C-I)
├── examples/                     exemplo existente, classpath do model
└── scripts/ + docs/              gates/contratos do reactor

artifact air-json → artifact air-java
package validation → package model
package model ✗→ validation; artifact air-java ✗→ air-json / infraestrutura
```

| Coordenada | Versão recomendada em 0C-I | Responsabilidade |
| --- | --- | --- |
| `io.github.gustavo2358:air-java-parent:pom` | `0.1.0-SNAPSHOT` | propriedades/plugins comuns e módulos; nenhuma dependência de runtime herdada |
| `io.github.gustavo2358:air-java:jar` | herda `0.1.0-SNAPSHOT` | modelo imutável e Validator estrutural atuais |
| `io.github.gustavo2358:air-json:jar` | herda `0.1.0-SNAPSHOT` | módulo reservado; dependência compile direta em `air-java:${project.version}` |

Versionamento Maven conjunto neste ciclo, sem release, deploy, BOM, relocation,
classifier de compatibilidade, flatten plugin ou JPMS novos. AIR `2.0.0` e binding
`1.0.0` são versões distintas da biblioteca. Futuro release deverá instalar/publicar
parent POM e ambos os artefatos como conjunto; publicar somente o JAR/POM do filho
não basta. Não reutilizar uma versão de release já publicada. SNAPSHOT exige pin
imutável de fonte e cache isolado; nome igual não prova proveniência.

Maven separa agregação de herança e permite que diretório e artifactId sejam
diferentes. Os filhos herdam groupId/version pelo parent e usam relativePath
`../pom.xml`. O root precisa de GAV distinto: packaging diferente não permite
repetir o mesmo GAV no reactor. A execução local confirmou B e rejeitou GAV
repetido. [POM Maven](https://maven.apache.org/guides/introduction/introduction-to-the-pom.html),
[reactor Maven](https://maven.apache.org/guides/mini/guide-multiple-modules.html).

## Destino de validation

**Manter dentro de air-model, no mesmo JAR air-java, com package inalterado.**
AirValidator usa model e JDK, não exige infraestrutura. Ambos os consumidores
usam API de validação na produção e nos testes; separá-la imporia uma dependência
e um ciclo de release adicionais para entregar o mesmo comportamento.
São 25 classfiles de validação frente a 283 do modelo, sem dependência externa
para economizar. Um caller pode construir/usar valores sem chamar AirValidator;
isso já é permitido. A presença de classes no JAR não obriga sua execução.

Módulo próprio permitiria excluir fisicamente essas classes e versionar validator
separadamente, mas não há consumidor ou política de release observados que exijam
isso. Custo: terceiro módulo de produto, mais pins, graph/gates/test fixtures e
compatibilidade de ValidationResult. Preservar a direção package model ✗→ validation
por bytecode entrega a separação necessária hoje. Reavaliar apenas diante de
necessidade medida, não por pureza ou antecipação de interfaces.

## Matriz comparativa

C é uma alternativa válida com dois módulos físicos: root `air-java-build:pom`
apenas aggregator; air-model mantém POM autônomo/GAV air-java; air-json tem POM
próprio sem herança, depende do modelo. Não mantém codec junto do núcleo.

| Critério | A: root air-java, modelo air-model | B: parent distinto, modelo air-java | C: aggregator sem herança |
| --- | --- | --- | --- |
| churn no cobol-lower | mínimo 6 arquivos executáveis/metadados + docs/pin | 0 GAV/import; pin/proveniência para adoção | igual B |
| churn no analysis-cfg | mínimo 5 + docs/pin/CI | 0 GAV/import; pin/CI para adoção | igual B |
| compatibilidade Maven | perde JAR atual; cache velho pode mascarar erro | GAV/JAR preservados; precisa parent instalado | GAV preservado; model POM autônomo |
| clareza de coordenadas | diretório/artifactId coincidem, mas troca identidade usada | pasta air-model contém artefato histórico air-java; documentar | root build distinto; configs independentes |
| risco de breaking change | resolução física quebra ambos | baixo; provar classes, parent, runtime vazio e cwd | baixo para API; risco de drift entre POMs |
| facilidade de pin | muda GAV e pin SHA | preserva GAV; atualiza só adoção de SHA | preserva GAV; versões duplicadas nos POMs |
| release/publicação | root POM + 2 novos JARs; migração coordenada | parent POM + 2 JARs; versão herdada conjunta | 2 JARs independentes; coordenação manual |

B vence pela compatibilidade provada e uma só configuração de build. A é rejeitada
por quebra desnecessária; C elimina o requisito de publicar parent, mas cobra
configurações duplicadas num repo com release conjunto. Não foi feito reactor C
completo: essa diferença decorre da herança ausente, não de um teste alegado.
Shim/relocation ou quarto projeto só para nome novo aumentariam resolução e risco
de transitividade sem melhorar a fronteira; não recomendados.

## Riscos e rollback

- **Root GAV duplicado:** Maven rejeitou o probe; usar air-java-parent, não mesmo GAV
  com packaging diferente. Não instalar POM aggregator sob identidade do JAR.
- **Parent ausente:** consumer externo falhou mesmo com JAR presente; instalar o
  reactor completo. Consumir o JAR cru no classpath não prova resolução Maven.
- **Cwd/suíte herdada:** falha real do exec:java; consertar lançamento, manter 172
  checks uma vez e falhar se módulo/resultado estiver ausente.
- **JSON transitivo sem referência em classes:** gate atual passou com dependência
  runtime Jackson sintética. Bytecode precisa ser combinado com grafo efetivo
  compile/runtime vazio do modelo, sem afrouxar sua allowlist.
- **Módulo ignorado/JAR stale:** módulos efetivos devem casar com política; clean,
  classe/JAR por módulo, nenhum wildcard silencioso de target antigo.
- **SNAPSHOT reaproveitado:** consumers hoje pinam fonte antiga; não chamá-los
  migrados só por manter a versão. Use cache isolado e hash/proveniência do novo SHA.
- **0B pendente/novos commits:** não escolher lib JSON ou atualizar lock por este ADR.

Rollback futuro é um commit de reversão de 0C-I, preservando este discovery e
abrindo registro de falha: restaurar root POM single-module/GAV air-java,
fontes/testes nos paths antigos, scripts, inventários, MANIFEST e CI/gates anteriores.
Remover apenas os arquivos criados por 0C-I via reversão revisada; não descartar
mudanças alheias nem usar reset/force-push. Executar full/scope e provar novamente
JAR/classes/consumo externo. Consumers ainda no pin antigo não mudam. Se já tiverem
adotado o pin novo, reverter seus pins/proveniência/CI em trabalhos próprios para
SHA conhecido ou SHA de reversão, nunca substituir release existente.

Como B preserva GAV e API, rollback não exige renomear dependências Java/Maven;
cache de teste deve ser refeito para não mascarar artefato velho. Se a causa for
parent/publicação ou compatibilidade não prevista, registrar evidência e reavaliar
C/coordenadas antes de nova tentativa. A reversibilidade topológica foi exercitada
restaurando parent e reinstalando baseline single-module em cache descartável.
